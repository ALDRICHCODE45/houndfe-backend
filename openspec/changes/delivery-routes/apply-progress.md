## Deviations from design / spec

1. **Partial unique index column names use camelCase, not snake_case.**
   The design document §4.3 sketches the partial unique index with
   `"tenant_id"` / `"sale_id"` (snake_case). Every existing migration in
   `prisma/migrations/` (e.g. `20260731230457_add_quotations_tables`)
   emits columns in camelCase — Prisma's default — and the user-supplied
   prompt instruction asked us to "check prisma/migrations/ for the exact
   snake_case column naming convention Prisma emits". Since the actual
   Prisma emission uses camelCase and the codebase precedent is
   camelCase, the migration uses `"tenantId"` and `"saleId"` in the
   index predicate. The `WHERE "activeRouteId" IS NOT NULL` predicate is
   unaffected by the casing choice.
2. **`@@unique([routeId, sortOrder])` instead of `@@unique([routeId, saleId])`.**
   The tasks document 1.2 lists `@@unique([routeId, saleId])` in the
   task description, but the design document §4.2 model block specifies
   `@@unique([routeId, sortOrder])`. The schema follows design.md (the
   authoritative input). The semantic intent — "a route cannot have two
   stops at the same position" — is preserved. The duplicate-sale case
   is enforced separately by the application pre-check in WU2
   (`DeliveryRouteSaleAlreadyInActiveRouteError`) and the ADR-7 partial
   unique index on `(tenantId, saleId) WHERE activeRouteId IS NOT NULL`,
   so no race window exists for a single sale joining the same route
   twice.
3. **No `prisma:migrate` script exists in `package.json`.** The
   `prisma:migrate` command referenced in tasks.md 1.3 and 1.9 is not
   present in the repo. We used `prisma validate` + `prisma generate`
   + `nest build` (per the parent prompt's gate) and authored the
   migration SQL by hand to match Prisma's emission (verified by
   `prisma migrate diff` against an empty schema). The parent owns the
   actual `prisma migrate deploy` step.
