## Deviations from tasks.md
- **None functional.** Tests exceed the 400-line budget significantly because the project convention requires a dedicated spec for every new layer (entity/repo/service/controller/filter/seeder/registry/chatbot-api service/chatbot-api controller). The implementation code itself is ~600 LOC + migration + 1.4K LOC of tests = ~2K LOC total. Within the design's `exception-ok` delivery decision.
- The `create-payment-detail.dto.ts` / `update-payment-detail.dto.ts` use `@Matches(/\S/)` for non-whitespace bankName / beneficiary (the plain `@IsNotEmpty()` validator does NOT reject whitespace-only strings).
- The `DomainExceptionFilter.details` spread uses `Object.assign(body, exception.details)` instead of `{...body, ...exception.details}` to keep TypeScript inference clean for the existing `body: Record<string, unknown>`.

## Risks / Notes
- **Lint warnings (pre-existing pattern):** all remaining lint complaints in the new spec files are `as any` casts in test mocks (e.g., `tenantPrisma as any`). The pre-existing `src/admin/admin-role.service.spec.ts` has 7 errors and 12 warnings of the same kind, so this is the project's accepted test pattern. The build (`nest build`) and full test suite are clean.
- **DTO whitespace validation:** `@IsNotEmpty()` only rejects empty strings (not whitespace). The DTO uses `@Matches(/\S/)` to ensure non-whitespace content.
- **DomainExceptionFilter in test setup:** the controller spec previously did NOT register `DomainExceptionFilter` globally. With the new `NO_ACTIVE_PAYMENT_DETAIL → 404` mapping, the controller spec now registers the filter so the `BusinessRuleViolationError` from the service layer is correctly translated. (Mirrors what `nest build` does in `main.ts`.)
