# Proposal — `quotation-product-iva` (Product IVA on Quotations)

Status: proposed

## Intent

Replace the DRAFT-wide editable tax rate on quotations with parent-product-derived IVA. Each quotation line snapshots the parent product's tax classification (`ivaRate` × `chargeProductTaxes`) at line creation and on every DRAFT reprice; classification-level IVA amounts are computed from those snapshots for the API; the PDF shows only the aggregate included-IVA. IVA-inclusive grand totals remain unchanged. SENT quotations never re-derive tax data from current products.

`PATCH /quotations/drafts/:id/tax-rate` is **deprecated** in this slice — it remains callable temporarily but MUST NOT affect the new product-derived IVA calculation; its later removal is a follow-up. `ivaBreakdown[]` exposes buckets only for the classifications actually represented by snapshot-complete lines (zero-amount buckets included when `IVA_0`, `IVA_EXENTO`, or `NOT_TAXABLE` lines are present); it does **not** always return all five buckets. If any quotation line lacks a complete tax snapshot, the API returns `ivaBreakdown: []` and the PDF omits the IVA row entirely — never a fabricated aggregate zero and never a partial breakdown. The legacy root `taxRate` column affected only the now-removed informational `taxCents` field; line and grand totals are and always were IVA-inclusive from product pricing.

## Business problem & goal

**Problem.** A draft quotation carries a single root `taxRate` (Float, default 0.16) editable via `PATCH /quotations/drafts/:id/tax-rate`. This is the only tax source quotations expose: `Quotation.toResponse()` returns `taxCents = round(totalCents * taxRate / (1 + taxRate))`. Critically, that `taxRate` value affected **only** the informational `taxCents` field on the response — it did NOT participate in `lineTotalCents`, `subtotalCents`, `discountCents`, or the grand `totalCents`. Line and grand totals are and always were IVA-inclusive because product unit prices are stored IVA-inclusive, not because of the root `taxRate`. Real customer quotes routinely mix `IVA_16`, `IVA_8`, `IVA_0`, `IVA_EXENTO`, and products flagged `chargeProductTaxes = false` — three different zero-tax meanings that today collapse into one editable decimal that produces a single ungrounded `taxCents` value. The PDF silently drops the field entirely (no IVA row was ever rendered); customers receive a quote whose API-side tax math has no correspondence to the products inside it.

**Goal.** A quotation's IVA reflects the actual products on each line. The API returns IVA amounts by classification so the frontend and internal analysis can act on per-product tax; the PDF keeps a single aggregate included-IVA line so the customer-facing document stays uncluttered. Line unit prices stay IVA-inclusive; the grand total does not move. SENT quotations never silently re-tax themselves when an admin later edits a product.

## Target users

- **Sales reps** building DRAFT quotations with mixed products — they get a quote that mirrors the catalog tax settings they configured for each product, with no editable override to mis-set.
- **Customers** receiving SENT quotations — they see one aggregate included-IVA amount on the PDF, with no per-rate breakdown that would expose the merchant's product-classification mix.
- **Tenant admins / catalog owners** configuring `chargeProductTaxes` and `ivaRate` on products — they get predictable, snapshot-based tax math on every quote that references their products, including quotes already sent.
- **Backend / frontend integrators** consuming `GET /quotations/:id` — they receive a documented `ivaBreakdown[]` shape they can render, ignore, or aggregate; the breakdown is the single source of truth for line tax.

## Scope

### In scope (backend only; DRAFT + SENT immutability)

- **Schema + migration (M1).** Add per-line tax snapshot fields to `QuotationItem` (nullable; no rewrite of existing rows):
  - `taxableBaseCents: Int?` — the IVA-exclusive base used as the classification input.
  - `ivaRateClassification: IvaRate?` — snapshot of the parent product's `ivaRate` enum (`IVA_16 | IVA_8 | IVA_0 | IVA_EXENTO`).
  - `chargeProductTaxesSnapshot: Boolean?` — snapshot of the parent product's `chargeProductTaxes`.
  - Persist the snapshot as the disambiguating pair `(ivaRateClassification, chargeProductTaxesSnapshot)` so the API can return three different buckets for the three zero-tax meanings (`IVA_0`, `IVA_EXENTO`, `chargeProductTaxes=false`).
  - **Do not** add a new enum value to `IvaRate`; the existing fields already disambiguate.
  - **Do not** drop `Quotation.taxRate` in this slice (see Compatibility / deprecation impact).
- **Line creation + reprice (`addItem`, `recomputePricingAndPromotions`).** Extend `ProductsService.getProductInfoForSale(productId, variantId)` to return tax metadata `{ ivaRate, chargeProductTaxes }` resolved from the parent product (variants inherit). `addItem` snapshots these on every new line. `recomputePricingAndPromotions` re-snapshots a repriced non-custom price-list line during DRAFT and re-derives `taxableBaseCents`.
- **Variants inherit parent.** No variant-level tax field is added; the variant line's snapshot is read from the parent product at snapshot time. Variants cannot introduce an independent tax classification in this slice.
- **Quotation response shape.** `Quotation.toResponse()` adds `ivaBreakdown: { classification, amountCents }[]` containing **only** the classifications actually represented by snapshot-complete lines (zero-amount buckets included when `IVA_0`, `IVA_EXENTO`, or `NOT_TAXABLE` lines are present; the array does not always return all five buckets). `taxRate` is removed from the response. `taxCents` is removed from the response — it was informational only and never participated in `lineTotalCents` or grand totals (see Compatibility).
- **Aggregate PDF amount (conditional).** `PdfGenerationService.buildQuotationProps()` passes one aggregate included-IVA amount (sum of breakdown buckets) to `QuotationA4Document` **only when every line is snapshot-complete**. The PDF then renders exactly one IVA line: no classification, no rate label, no per-rate breakdown, no per-line tax. If any line lacks a complete snapshot, the PDF omits the IVA row entirely (never a fabricated aggregate zero, never a partial breakdown).
- **SENT immutability.** Public service methods continue to reject mutations on non-DRAFT quotations. Once a quote is `SENT`, line tax snapshots are frozen and re-reading the quote MUST NOT re-resolve them from current product data. Historic SENT/EXPIRED rows that predate the migration remain null-snapshot; because at least one of their lines lacks a complete snapshot, the API returns `ivaBreakdown: []` and the PDF omits the IVA row entirely — no fabricated breakdown.
- **Deprecation of the override endpoint.** `PATCH /quotations/drafts/:id/tax-rate` is **deprecated** in this slice — the route, controller handler, and `SetQuotationTaxRateDto` remain in place and the endpoint stays callable temporarily, but the handler MUST NOT influence the new product-derived IVA calculation, the `ivaBreakdown[]` response, or the PDF aggregate. The response emits a deprecation signal (header) on the existing path. The root `Quotation.taxRate` column is retained on the row but ignored by the response/recompute path (see Compatibility). Removing the route and DTO is a follow-up change.
- **Tests.** Co-located Jest unit specs for `Quotation` / `QuotationItem`, `QuotationsService.addItem` and `recomputePricingAndPromotions`, the response-shape projection, the repository round-trip, and the PDF prop mapping / template. `pnpm test` and `pnpm build` pass.

### Out of scope / non-goals

- **IEPS**, including `Product.iepsRate`, line-level IEPS snapshots, IEPS totals, or IEPS in the PDF.
- **CFDI generation** or any other fiscal-document emission. This slice is non-compliance and does not produce regulated documents.
- **Sales-tax changes.** `SalePayment`, `SalePaymentMethod`, sale-side IVA math, refunds, outbox consumers, and reporting are untouched.
- **Retroactive rewriting of sent quotation rows.** Existing `SENT` / `EXPIRED` quotations MUST NOT be rewritten; their snapshots remain null and the API/PDF treat them as "no tax breakdown available". The migration adds nullable columns with neutral defaults only.
- **Variant-level tax fields.** Variants inherit parent tax behavior; no independent variant classification or tax-enable override is added.
- **Removal of the deprecated override endpoint.** Dropping `PATCH /quotations/drafts/:id/tax-rate`, its handler, and `SetQuotationTaxRateDto` is out of scope for this slice; it is a follow-up change.
- **External fiscal research.** Was offered, unselected, and recorded as adding no material value to this non-compliance slice; documented in `explore.md`.
- **Implementation, push, or PR work.** This proposal records the contract only.

## Requirements outline (invariants — MUST-level)

- **(a) IVA-inclusive preservation.** Line unit prices are IVA-inclusive from product pricing. Recomputing line tax MUST NOT change `lineTotalCents`; the quotation grand total MUST equal the previous inclusive grand total for the same line set. The legacy root `taxRate` column never participated in `lineTotalCents`, `subtotalCents`, `discountCents`, or the grand `totalCents`; only the now-removed informational `taxCents` was derived from it. When all lines are snapshot-complete, the aggregate IVA amount equals `grandTotal − Σ taxableBaseCents` (after discounts); otherwise the API returns `ivaBreakdown: []` and the PDF omits the row.
- **(b) Bucket set reflects represented classifications.** `ivaBreakdown[]` includes **only** the classifications actually represented by snapshot-complete lines on the quotation. Zero-amount buckets (`IVA_0`, `IVA_EXENTO`, `NOT_TAXABLE`) appear in the array **only when at least one snapshot-complete line carries that classification**; the array does not always return all five buckets. The three zero-tax meanings MUST remain distinct whenever each is present: `IVA_0`, `IVA_EXENTO`, and `chargeProductTaxes=false` (rendered as `NOT_TAXABLE`) each map to a separate bucket. The snapshot pair `(ivaRateClassification, chargeProductTaxesSnapshot)` is the disambiguation; the implementation may pick the persisted identifier shape freely as long as the three buckets stay distinguishable when represented.
- **(c) Variant inherits parent.** A variant line MUST inherit its parent product's `ivaRate` and `chargeProductTaxes` at snapshot time. Variants MUST NOT introduce an independent tax classification or override in this slice.
- **(d) SENT immutability.** Once a quotation is `SENT` (or `EXPIRED`), line tax snapshots MUST NOT be re-resolved from current product data on read; the API and the PDF MUST use the stored snapshots. No data migration rewrites existing sent rows.
- **(e) PDF aggregate-only, conditional on snapshot completeness.** The PDF MUST show exactly one IVA amount (the sum of all breakdown buckets) **when every line on the quotation is snapshot-complete**. It MUST NOT show a classification label, a per-rate breakdown, a rate percentage, or per-line tax amounts. If any line lacks a complete snapshot, the PDF MUST omit the IVA row entirely — never a fabricated zero.
- **(f) DRAFT-only mutation, unchanged.** Deprecating the editable `taxRate` MUST NOT widen the surface where non-DRAFT quotations can be mutated; existing `ensureDraft()` guards stay. The deprecated `PATCH .../tax-rate` route continues to call `ensureDraft()` and remains DRAFT-only.
- **(g) Tenant isolation + scope.** No change to existing tenant scoping or controller authorization on `/quotations/*`; the new snapshot fields are part of the existing aggregate.
- **(h) Strict DTO validation.** The new response field uses a closed enum union for classification; `ivaBreakdown[]` is validated with `class-validator` consistent with the bootstrap `whitelist` / `forbidNonWhitelisted` pipe.
- **(i) Deprecation signal.** The deprecated `PATCH .../tax-rate` response emits a deprecation signal (header) so any active caller can detect the upcoming removal.

## Business rules

- **Snapshot at line creation.** Every line created via `addItem` snapshots `{ ivaRateClassification, chargeProductTaxesSnapshot, taxableBaseCents }` from the parent product at that moment. The snapshot survives any later product edit.
- **Snapshot at reprice.** When `recomputePricingAndPromotions` re-resolves a non-custom price-list line during DRAFT, the snapshot is re-read from the **current** parent product (the line is being repriced, not just re-taxed). SENT lines never reprice.
- **`chargeProductTaxes=false` forces zero.** A product with `chargeProductTaxes=false` snapshots `chargeProductTaxesSnapshot=false` regardless of its `ivaRate`. The IVA amount for that line is 0, surfaced under a `NOT_TAXABLE` classification bucket that is distinct from both `IVA_0` and `IVA_EXENTO` whenever such a line is present on the quotation.
- **`IVA_0` vs `IVA_EXENTO` stay distinct when present.** Both produce 0 amount, but `ivaRateClassification` is preserved on the snapshot; the API response exposes them as separate buckets **when each is represented** by at least one snapshot-complete line. No implementation logic may collapse them, and neither bucket is fabricated for absent classifications.
- **Discount handling.** Classification is computed against the **post-discount line base** to preserve invariant (a). Promotion discounts reduce `taxableBaseCents` before classification; line-level math still yields the same inclusive line total.
- **Variant inheritance.** A variant line's snapshot is read from the variant's parent product. No code path resolves a variant's own tax state in this slice.
- **SENT freeze.** `send` renders from the DRAFT response and transitions to SENT; after that, all reads MUST use stored snapshots. No read-side code re-resolves tax from the products table.
- **PDF aggregate (conditional).** `QuotationA4Document` receives exactly one IVA amount (sum of breakdown buckets) and a label that does not disclose classification or rate **only when every line on the quotation is snapshot-complete**. The existing subtotal / discount / total layout is unchanged; the new IVA line is added conditionally. If any line lacks a complete snapshot, the PDF omits the IVA row entirely — never a fabricated aggregate zero, never a partial breakdown.
- **No live product lookup on read.** Public service reads MUST NOT call `ProductsService` to resolve tax for an existing SENT/EXPIRED line. New drafts may still call it for current-price resolution; the snapshot is stored before persistence.
- **Legacy rows.** Pre-migration lines carry `null` snapshots; if **any** line on a quotation lacks a complete snapshot (whether pre-migration or otherwise), the API returns `ivaBreakdown: []` and the PDF omits the IVA row entirely. No fabricated aggregate zero, no partial breakdown, no backfill. A quotation becomes eligible for the new breakdown only after its next DRAFT mutation that produces a complete snapshot for every line.

## Rollback plan

The change is additive at the persistence layer (new nullable columns; `Quotation.taxRate` column preserved) and reductive at the API/PDF surface (one response field removed, one response field added, one deprecated endpoint kept, conditional PDF rendering). Code and data rollbacks are independent.

1. **Code rollback (single revert).** Reverts the `Quotation` / `QuotationItem` snapshot fields, the `ivaBreakdown[]` response field, the conditional PDF rendering, the `getProductInfoForSale` widening, the deprecation signal on `PATCH .../tax-rate`, and the new tests. After revert, the deprecated route continues to persist the root `taxRate`; `taxCents` returns to its old shape on the response; the PDF regains no IVA row; and the new snapshot fields are simply ignored.
2. **Migration rollback (data).** The new columns are nullable and additive; a follow-up additive migration can `DROP COLUMN` them in any order without affecting existing rows. Historic sent rows retain their `null` snapshots but become unreadable by the reverted code (the columns are simply ignored).
3. **No backfill required.** Because the migration is conservative-neutral on historic rows, no data-fix migration is needed before or after a code revert.
4. **Verification after rollback.** `pnpm test` and `pnpm build`; smoke-test a DRAFT add-item path that used the new snapshot fields (must 500 after revert because the code no longer knows them — acceptable, no caller writes to them any more); smoke-test a SENT read (must return old `taxCents`, no `ivaBreakdown`, PDF renders no IVA row); smoke-test the deprecated `PATCH .../tax-rate` (still callable, still persists `taxRate` on the row, no deprecation signal).

## Success criteria

- `POST /quotations/drafts/:id/items` snapshots the parent product's `ivaRate` and `chargeProductTaxes` on the line.
- `recomputePricingAndPromotions` re-snapshots a repriced DRAFT line; SENT/EXPIRED lines never re-snapshot.
- `PATCH /quotations/drafts/:id/tax-rate` remains callable, persists the legacy root `taxRate` on the row, emits a deprecation signal on the response, and **does not** affect the new product-derived IVA calculation, the `ivaBreakdown[]` response, or the PDF aggregate. Route removal is a follow-up.
- `Quotation.toResponse()` includes `ivaBreakdown: { classification, amountCents }[]` containing only the classifications actually represented by snapshot-complete lines on the quotation — zero-amount buckets (`IVA_0`, `IVA_EXENTO`, `NOT_TAXABLE`) appear only when a line carrying that classification is present. The array does **not** always return all five buckets; if the quotation has no snapshot-complete lines the array is empty.
- For any line set where every line is snapshot-complete, `Σ lineTotalCents` is unchanged after recompute and `Σ ivaBreakdown.amountCents` equals `grandTotal − Σ taxableBaseCents` after discounts.
- The PDF renders exactly one IVA line per quote, labeled without classification or rate percentage, **only** when every line is snapshot-complete.

- Pre-migration SENT/EXPIRED rows are surfaced exactly as null-snapshot rows: `ivaBreakdown: []` and PDF IVA row omitted; no fabricated historical tax.

## Proposal question round

The orchestrator resolved the four product decisions (inclusive grand totals; distinct zero-tax classifications; API-vs-PDF split; variant inheritance) before this proposal. The compatibility decisions in this proposal (deprecate-not-remove; empty `ivaBreakdown` + omitted PDF row on null snapshots; represented-only bucket set; `taxCents` was informational only) have also been resolved with the user. No further proposal-shaping questions are open. If a reviewer wants to revisit the contract, the assumptions most worth confirming are:

1. **Deprecating `PATCH .../tax-rate` in this slice (resolved).** The endpoint stays callable temporarily and emits a deprecation signal; its payload MUST NOT affect the new product-derived IVA calculation. Route removal is a follow-up. This avoids hard-breaking any unmeasured caller while keeping the controller surface explicit about the upcoming removal.
2. **Null snapshot semantics for any line lacking a complete snapshot (resolved).** Surfacing the quotation as `ivaBreakdown: []` and omitting the PDF IVA row entirely is the chosen safe default — never a fabricated aggregate zero and never a partial breakdown. Alternatives (an explicit "UNKNOWN" classification; a one-shot backfill that snapshots from current products at deploy time) are possible if a later slice prefers different legacy semantics.
3. **Represented-only bucket set (resolved).** `ivaBreakdown[]` includes only the classifications actually represented by snapshot-complete lines; zero-amount buckets appear only when zero-tax lines are present. Alternatives (always returning all five buckets; four buckets collapsing `IVA_0` + `IVA_EXENTO` + `chargeProductTaxes=false`) are simpler but lose the distinctness the confirmed contract requires.

## Resolved decisions (rationale encoded)

1. **Snapshot at line time, not at read time.** SENT immutability demands frozen snapshots; live resolution would re-tax historical quotes on every product edit.
2. **Three distinct zero-tax classifications.** `chargeProductTaxes=false` is a separate business intent (`do not charge IVA`) from `IVA_0` (rate is 0%) and `IVA_EXENTO` (exempt by classification); collapsing them on the API would lose the meaning the product domain already keeps.
3. **API breakdown, PDF aggregate.** Customers see one number; the backend exposes the breakdown so the frontend and any internal analysis can act on it. A per-rate PDF would expose product-classification mix to customers.
4. **Variant inherits parent.** No variant-level tax fields exist; adding them would expand scope to a tax-attribute redesign on `Variant` and to migration of every variant row, neither of which this slice is prepared to absorb.
5. **`Quotation.taxRate` column and `PATCH .../tax-rate` route kept (deprecated).** The column and route stay in place so the legacy path continues to behave observably: the route persists the column on the row, the response emits a deprecation signal, and neither influences the new product-derived IVA calculation. Both are dropped in a follow-up change once the deprecation window has elapsed. This preserves the revert path (legacy code keeps working unchanged if the snapshot pipeline is reverted) and respects any unmeasured caller that may still hit the route.
6. **No backfill of historic SENT/EXPIRED rows.** Invariant (d) forbids rewriting historical data; null snapshots are the honest representation of pre-migration rows.

Forecast: ~600–900 lines added across schema, entity, service, controller, repository, DTO, PDF template, deprecation signal, and new specs. ## Key Learnings

1. The proposal must surface the three distinct zero-tax classifications explicitly because the value-object treats all three as 0% while the product domain already separates them.
2. SENT immutability is the binding constraint that forces snapshot-at-write over live resolution; documenting that constraint up front prevents reviewers from proposing re-resolve on read.
3. PDF aggregate-only and API classification breakdown must be stated as two separate invariants because they protect two different audiences (customer vs internal).
